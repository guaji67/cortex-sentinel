# 让看板接住研究，而不是让研究迎合看板

此入口由哨兵「AI 规则」管理来源与版本。需要维护协议时改登记的正本，不改已安装副本；
本机差异会暂停覆盖。安装成功不能当作 AI 已读取或产品已验收的证据。

这是 **Cortex 哨兵内置工作台**的维护协议。前后端、协议与工具在 cortex-sentinel
同一仓、随同一个 App 安装更新；不要另起网页服务、写固定机器分工或每次靠 SSH 更新。

先和用户把问题聊清楚。板块怎么拆、是否分层、内容多长、用文档还是图，都由实际问题决定。
可以先放一段自由正文，逐步长出结构；不要求在开工时填满字段，不为了卡片整齐删掉不确定性。

## 读与写

本机部署坐标放 `~/.config/cortex-board/location.json`，只含 client 路径、profile 路径与看板地址。
读取该文件后，用它给出的 `client.py --profile <profile> overview` 或 `read <id>`。
不要打印 profile 内容；它只用于签名，不写进工单、正文、日志或网页。

共用的只是身份和链接：稳定 id、title、kind、track。其他字段按需要生长。
kind=track 是板块入口；area 是任意层级子块（parent 可选）；note 可写自由 body；relation 记录接缝；problem 才是要独立追踪的具体问题。
地图上用简短 title、自由 group、可选 status_label/color；正文独立，不能为了格子删研究。
保留维护者给颜色的原意（覆盖、交付、责任等），不统一曲解成健康或验收。
板块不是顶栏导航项；新登记后从目录进入。machine/owner 只记录明确的当期安排，绝不从板块名推断。
新增板块时先向有对应授权的维护入口登记 track；权限不覆盖它时报告权限缺口，不借用其他板块身份。
任意资料可放 references；前端暂不认识的扩展字段仍保留、可供 AI 阅读。接口细则读看板 `/api/guide`，不要求重读整个项目。

写回事件只有五项：event_id、id、kind、base_revision、patch。先读后改，只更新自己的内容。
创建时 base_revision=0；更新时使用刚读到的 revision；运行 `client.py --profile <profile> update --file <事件.json>` 后再次 read 验证。
409 表示别人先更新了，重读并合并；超时先 read/history 查是否已写入，必要时重发同一 event_id；403 不绕过。

## 影响进度判断的结论必须有依据

- 工单、子任务、研究发现不直接等于 bug；同一问题跨块只留一个问题 id，以 relation 引用。
- 代码已合、已装目标机、用户操作已验分开写。verified 的 evidence 要能回答在哪台、什么版本、做了什么、预期和实际、何时验、证据在哪里。
- 票关了、PR 合了、AI 说做完了，都不自动改变验收状态；历史资料收口只记 source_closed，排除/归并记 dismissed，不记修好。
- 接缝可先 proposed；confirmed 要给依据，但不据此越权改另一个板块。
- 未知就保留未知。不用 CPU、提交数量或签到频率给自己证明绩效。

## 什么时候更新

形成新结构理解、确认问题、改变主责、推进交付、完成验收或发现回归时，顺手更新对应内容。
没有新信息不刷空心跳、不写装样子的日报。完成后回读验证总览与板块页已反映变化。
现有板块 HTML 可以继续维护：哨兵托管登记过的本地发布器，经局域网汇入来源说明，保留分组、图例和研究正文，不自动改验收账。
新电脑先安装哨兵，选择连接已有共享账；只读配对不代表 AI 写权限。由共享账主机
随包 authorize.py 为新维护者发放限定板块 profile（密钥文件只安全传一次，不进票或 git）。
原图兼容发布器需要 Python 3；原生工作台与 JSON API 不需要额外解释器。
若 `location.json` 提供 `legacy_sources`，维护原图时写它指向的实际文件；下载夹可能只是兼容链接，不用原子替换把链接变成孤立副本。
这不要求每次 SSH，也不要求全部板块先画齐。当前 AI host 若没加载本 Skill，可在当前会话明确读取本文件；新会话正常发现。
